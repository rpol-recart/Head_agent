# Формулирование задачи для подчинённого

## Зачем это нужно

Руководитель часто формулирует задачу кратко: «Сидоров, сделай модель по дефектам».
Этот скилл помогает **развернуть** краткую фразу в полноценную, понятную сотруднику задачу.

## Шаблон задачи

### 1. Title (заголовок)
**Формула:** `[Глагол] + [Объект] + [Контекст]`

Плохо: «Сделать модель»
Хорошо: «Обучить модель предсказания дефектов литья на данных цеха №3»

### 2. Description (описание)
- Что именно нужно сделать
- Какой результат ожидается
- Входные данные: где лежат, в каком формате
- Целевая метрика (если есть)

### 3. Acceptance Criteria (критерии приёмки)
Конкретный чеклист — по нему проверяем «сделано или нет»:
- Каждый критерий — измеримый и проверяемый
- Примеры:
  - «F1-score > 0.85 на hold-out тестовой выборке»
  - «REST API обёртка (FastAPI) с документацией»
  - «Jupyter notebook с EDA и обоснованием выбора модели»
  - «Код прошёл код-ревью и CI pipeline зелёный»

### 4. Context Notes (контекст)
- Почему задача важна (бизнес-ценность)
- Как вписывается в проект
- Ссылки на документы, данные, связанные задачи
- Информация из аналогичных проектов

### 5. Метаданные
- Assignee (исполнитель)
- Priority (P0–P3)
- Estimated hours (с учётом калибровки)
- Deadline

## Процесс делегирования

```
1. Руководитель: "Поручи Сидорову модель по дефектам"

2. Система формулирует черновик:
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Title: Обучить модель предсказания дефектов литья
   Description: ...
   Критерии приёмки:
     ✓ ...
     ✓ ...
   Контекст: ...
   Сидоров | P1 | 24ч | до 28.02
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Подтвердить? Или скорректировать?

3. Руководитель вносит правки или подтверждает

4. Система:
   - Ставит статус ASSIGNED
   - Устанавливает чекпоинт (полпути до дедлайна)
   - Напоминает в день чекпоинта
```

## Автоматический чекпоинт

После назначения задачи:
- **Дедлайн задан:** первый чекпоинт = дедлайн / 2
- **Дедлайн не задан:** чекпоинт через 3 рабочих дня
- На чекпоинте спросить: прогресс %, блокеры, нужна ли помощь
