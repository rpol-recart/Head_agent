# DS Team Management Agents — Общее видение системы

## 1. Контекст и проблема

**Роль:** Руководитель отдела Data Science в металлургической компании.
**Команда:** 8 специалистов (DS/ML-инженеры, аналитики данных).
**Вызовы:**
- Множество параллельных проектов с разными заказчиками внутри компании
- Необходимость точной оценки сроков и трудозатрат
- Контроль загрузки каждого сотрудника и перераспределение задач
- Анализ входящих технических заданий (ТЗ) от бизнес-заказчиков
- Управление приоритетами в условиях ограниченного ресурса команды
- Отсутствие единой системы, объединяющей планирование, мониторинг и аналитику

---

## 2. Целевое состояние

Мультиагентная система — **цифровой помощник руководителя**, которая:

1. **Снижает когнитивную нагрузку** на руководителя, автоматизируя рутину планирования и мониторинга
2. **Повышает прозрачность** состояния проектов и загрузки команды
3. **Помогает принимать решения**, а не принимает их за человека
4. **Учится на опыте** — улучшает оценки и рекомендации со временем

### 3.1. Orchestrator Agent (Координатор)

**Роль:** Единая точка входа для руководителя. Маршрутизирует запросы к нужным агентам, агрегирует результаты.

**Функции:**
- Принимает запрос на естественном языке от руководителя
- Определяет какие агенты нужно задействовать
- Собирает и синтезирует ответы от подагентов
- Управляет приоритетом выполнения между агентами
- Формирует итоговый ответ руководителю

**Пример взаимодействия:**
> «Кто из команды может взять новый проект по предиктивному качеству на следующей неделе?»
> → Координатор запрашивает Team Analytics (загрузка) + Scheduler (расписание) + Task Monitor (текущие задачи) → синтезирует ответ

---

### 3.2. Task Monitor Agent (Мониторинг задач)

**Роль:** Отслеживание состояния всех проектов и задач команды.

**Функции:**
- Парсинг и синхронизация с трекерами задач (Jira, Youtrack, Notion и др.)
- Отображение текущего статуса каждого проекта
- Выявление «застрявших» задач (нет прогресса N дней)
- Отслеживание дедлайнов и раннее предупреждение о рисках срыва
- Мониторинг блокировок между задачами

**Ключевые метрики:**
| Метрика | Описание |
|---------|----------|
| Прогресс проекта | % выполнения по вехам |
| Velocity команды | Скорость закрытия задач (story points / неделя) |
| Blocked tasks | Задачи, ожидающие внешнего ввода |
| Overdue tasks | Просроченные задачи с указанием причин |
| Pipeline health | Соотношение backlog / in progress / done |

### 3.3. Team Analytics Agent (Аналитика команды)

**Роль:** Анализ загрузки, эффективности и компетенций каждого сотрудника.

**Функции:**
- Расчёт текущей и прогнозной загрузки каждого члена команды
- Анализ распределения времени по типам активностей (разработка, ресёрч, встречи, код-ревью)
- Выявление дисбалансов нагрузки в команде
- Рекомендации по перераспределению задач
- Отслеживание роста компетенций сотрудников (матрица навыков)

**Модель сотрудника:**
```
Employee {
  name: string
  role: "junior_ds" | "middle_ds" | "senior_ds" | "ml_engineer" | "analyst"
  skills: Map<SkillDomain, ProficiencyLevel>    // напр. {CV: senior, NLP: middle, tabular: expert}
  current_load_hours: number                     // текущая загрузка (ч/неделя)
  max_capacity_hours: number                     // максимальная ёмкость (ч/неделя)
  active_projects: Project[]
  availability_calendar: Calendar                // отпуска, больничные, обучение
  historical_performance: PerformanceRecord[]    // история для калибровки оценок
}
```

**Визуализации:**
- Тепловая карта загрузки команды по неделям
- Radar-чарт компетенций каждого сотрудника
- Burndown/burnup по проектам

### 3.4. TZ Analyst Agent (Анализ технических заданий)

**Роль:** Разбор входящих ТЗ от заказчиков, оценка рисков, сроков и стоимости.

**Функции:**
- Структурирование неформализованных ТЗ в стандартный формат
- Декомпозиция ТЗ на задачи с оценкой трудозатрат (в человеко-часах)
- Оценка рисков: технических, данных, организационных
- Сравнение с аналогичными завершёнными проектами (из памяти)
- Формирование предварительного плана проекта

**Структура оценки ТЗ:**
```
TZ_Assessment {
  summary: string                          // краткое описание задачи
  business_value: "high" | "medium" | "low"
  complexity: "S" | "M" | "L" | "XL"

  decomposition: [
    { task: string, hours_optimistic: number, hours_realistic: number, hours_pessimistic: number }
  ]

  total_estimate: {
    hours_min: number
    hours_expected: number                 // PERT-взвешенная оценка
    hours_max: number
  }

  risks: [
    { category: string, description: string, probability: "high"|"med"|"low", impact: "high"|"med"|"low", mitigation: string }
  ]

  required_skills: SkillDomain[]
  recommended_team: string[]               // предложение по составу
  similar_projects: ProjectReference[]     // ссылки на аналоги из памяти
  data_requirements: DataAssessment        // оценка доступности и качества данных
}
```

**Формула оценки (PERT):**
```
Expected = (Optimistic + 4 * Realistic + Pessimistic) / 6
```

### 3.5. Scheduler Agent (Планировщик)

**Роль:** Управление рабочим временем руководителя и распределение задач команды по приоритетам.

**Функции:**
- Формирование оптимального расписания на день/неделю для руководителя
- Приоритизация задач по матрице Эйзенхауэра + бизнес-ценность
- Предложение назначений задач на конкретных сотрудников (с учётом загрузки и навыков)
- Выявление конфликтов расписания и ресурсных конфликтов
- Управление буфером времени (резерв на незапланированные задачи)

**Модель приоритизации:**
```
Priority = f(business_impact, deadline_proximity, dependency_blocking, strategic_alignment)

Категории:
  P0 — Критично: блокирует производство / бизнес-процесс
  P1 — Срочно: дедлайн < 1 неделя, высокая бизнес-ценность
  P2 — Важно: стратегические задачи, дедлайн > 1 неделя
  P3 — Плановые: улучшения, техдолг, обучение
```

#### 3.5.1. Ввод задач через чат и автопривязка к проектам

Руководитель вводит задачи в свободной форме прямо в чат. Система **автоматически**:

1. **Распознаёт задачу** — отличает ввод задачи от обычного вопроса или команды
2. **Привязывает к проекту** — по ключевым словам, упомянутым людям, контексту диалога
3. **Классифицирует тип** — определяет категорию задачи (см. ниже)
4. **Оценивает длительность** — на основе типа и исторических данных
5. **Подтверждает** — показывает как поняла задачу, просит подтвердить или скорректировать

**Пример ввода:**
```
Руководитель: "Позвонить Краснову из цеха 3 по данным для проекта дефектов"

Система:
  Задача принята:
  ├── Текст: Позвонить Краснову — обсудить данные
  ├── Проект: Предсказание дефектов литья (цех №3)  [автопривязка]
  ├── Тип: КОММУНИКАЦИЯ (звонок)
  ├── Оценка: ~15 мин
  └── Приоритет: P1 (блокирует получение данных для проекта)

  Всё верно? Или скорректировать?
```

```
Руководитель: "Подготовить презентацию результатов по шихте для совещания в пятницу"

Система:
  Задача принята:
  ├── Текст: Подготовка презентации результатов
  ├── Проект: Оптимизация шихты  [автопривязка]
  ├── Тип: ГЛУБОКАЯ РАБОТА (подготовка материалов)
  ├── Оценка: ~2ч
  ├── Дедлайн: пятница, 14 февраля
  └── Приоритет: P1 (привязан к совещанию)

  Ставлю в расписание на четверг утро (свободный блок для фокусной работы)?
```

**Механизм автопривязки к проекту:**
```
Шаг 1: Извлечь ключевые сущности из текста задачи
        → имена людей, названия цехов, технические термины

Шаг 2: Поиск по активным проектам (fuzzy match)
        → "цех 3" + "дефекты" → проект "Предсказание дефектов литья"
        → "Сидоров" + "шихта" → проект "Оптимизация шихты"

Шаг 3: Учёт контекста диалога
        → если 5 минут назад обсуждали проект X, новая задача скорее всего про X

Шаг 4: Если не удалось привязать → спросить руководителя
        → "К какому проекту отнести эту задачу? Или это отдельная задача?"

Шаг 5: Запомнить связку для будущего обучения
        → "Краснов" всегда связан с "цех 3" → запомнить
```

#### 3.5.2. Классификация задач по типам

Каждая задача автоматически получает один из трёх типов, определяющих **как** она планируется в расписании:

```
┌─────────────────────────────────────────────────────────────────────┐
│                     ТИПЫ ЗАДАЧ РУКОВОДИТЕЛЯ                        │
├──────────────────┬──────────────────┬───────────────────────────────┤
│   QUICK          │   COMMUNICATION  │   DEEP WORK                  │
│   Быстрые        │   Коммуникации   │   Глубокая работа            │
├──────────────────┼──────────────────┼───────────────────────────────┤
│ < 15 мин         │ 15-60 мин        │ > 1 час                      │
│                  │                  │                               │
│ - Согласования   │ - Звонки         │ - Анализ ТЗ                  │
│ - Быстрые ответы │ - Встречи        │ - Подготовка презентаций     │
│ - Апрувы в Jira  │ - Переписка      │ - Код-ревью сложных PR      │
│ - Резолюции      │ - One-on-one     │ - Стратегическое планирование│
│ - Чтение писем   │ - Stand-up       │ - Написание отчётов          │
│                  │ - Демо заказчику  │ - Проектирование архитектуры │
├──────────────────┼──────────────────┼───────────────────────────────┤
│ Группировать     │ Группировать     │ Планировать цельными блоками │
│ в пакеты по      │ в коммуникацион- │ 1.5-2ч без прерываний,       │
│ 30 мин           │ ные окна         │ утро — приоритет             │
└──────────────────┴──────────────────┴───────────────────────────────┘
```

**Правила автоклассификации:**
```
Task_Type classify(task_text):
  triggers_quick = ["согласовать", "апрув", "подтвердить", "глянуть", "ответить"]
  triggers_comm  = ["позвонить", "встреча", "обсудить", "созвон", "написать", "переговорить"]
  triggers_deep  = ["подготовить", "проанализировать", "разработать", "написать отчёт",
                     "ревью", "презентация", "стратегия", "архитектура"]

  // + контекстный анализ LLM для неоднозначных случаев
  // + обучение на коррекциях руководителя
```

#### 3.5.3. Правило 60% — защита от перегрузки

**Принцип:** Запланированные задачи занимают **не более 60%** рабочего дня. Оставшиеся 40% — буфер на незапланированное.

**Почему 60%:**
- Руководитель постоянно сталкивается с прерываниями (срочные вопросы, эскалации)
- Без буфера каждый форс-мажор ломает весь план
- 60% — это реалистичный, достижимый план, который не вызывает стресса

**Расчёт для 8-часового дня:**
```
Рабочий день: 8 часов = 480 минут

ПЛАНИРУЕМЫЕ задачи (макс. 60%):  288 мин = 4ч 48мин
├── Deep Work блоки:             макс. 2 блока × 1.5-2ч = 3-4ч
├── Communication окна:          макс. 1-2 окна × 30-60мин
└── Quick пакеты:                макс. 1-2 пакета × 15-30мин

БУФЕР (мин. 40%):               192 мин = 3ч 12мин
├── Незапланированные вопросы:   ~60 мин
├── Эскалации и срочные задачи:  ~60 мин
├── Переходы между задачами:     ~30 мин
└── Свободный резерв:            ~42 мин
```

**Как система это контролирует:**
```
При добавлении каждой задачи в расписание:

  total_planned = sum(задачи в расписании на день)

  if total_planned + new_task.duration > 0.6 * working_day:
      Система: "День заполнен на 60%. Добавить задачу сверх лимита?
                Варианты:
                1. Добавить — но учтите, буфер сократится
                2. Перенести на завтра
                3. Заменить — убрать менее приоритетную задачу
                4. Делегировать — назначить на сотрудника"
```

**Пример сформированного дня:**
```
Система: План на среду, 12 февраля
         Загрузка: 4ч 30мин / 4ч 48мин (94% от лимита 60%)

  ┌─ DEEP WORK ──────────────────────────────────────┐
  │ 09:00-10:30  Анализ ТЗ от цеха №3               │  [Предсказание дефектов]
  │              (подготовка декомпозиции и оценки)    │
  └──────────────────────────────────────────────────┘
  ┌─ QUICK ──────────────────────────────────────────┐
  │ 10:30-11:00  Пакет быстрых задач (6 шт.)        │
  │              ✓ Апрув PR Петровой                  │  [NLP-классификатор]
  │              ✓ Ответ Краснову по доступу к данным │  [Предсказание дефектов]
  │              ✓ Согласование отпуска Козлова       │  [Команда]
  │              ✓ Резолюция на закупку GPU           │  [Инфраструктура]
  │              ✓ Подтверждение scope спринта        │  [Оптимизация шихты]
  │              ✓ Ответ HR по вакансии               │  [Команда]
  └──────────────────────────────────────────────────┘
  ┌─ COMMUNICATION ──────────────────────────────────┐
  │ 11:00-11:30  Stand-up с командой                 │
  │ 14:00-14:45  Встреча с заказчиком (шихта)        │  [Оптимизация шихты]
  └──────────────────────────────────────────────────┘
  ┌─ DEEP WORK ──────────────────────────────────────┐
  │ 15:00-16:30  Код-ревью ML-pipeline Сидорова      │  [Оптимизация шихты]
  └──────────────────────────────────────────────────┘

  ░░ БУФЕР (3ч 30мин) — свободно для незапланированного ░░

  В очереди на завтра (не влезло):
  - Подготовка месячного отчёта для директора (2ч, DEEP WORK)
  - Созвон с IT по инфраструктуре (30мин, COMMUNICATION)
```

#### 3.5.5. Память задач: что система запоминает

Каждая введённая задача сохраняется навсегда и обогащает контекст:

```
TaskRecord {
  id: uuid
  raw_input: string                    // исходный текст из чата
  parsed: {
    action: string                     // "позвонить", "подготовить" и т.д.
    subject: string                    // о чём задача
    people: string[]                   // упомянутые люди
    project: ProjectRef                // привязка к проекту
  }
  classification: {
    type: "quick" | "communication" | "deep_work"
    estimated_minutes: number
    priority: "P0" | "P1" | "P2" | "P3"
  }
  scheduling: {
    planned_date: date
    planned_slot: TimeSlot
    actual_start: datetime | null
    actual_end: datetime | null
  }
  outcome: {
    status: "done" | "postponed" | "delegated" | "cancelled"
    actual_minutes: number | null      // фактическое время
    notes: string | null               // комментарий руководителя
    delegated_to: string | null        // кому делегировано
    follow_up_tasks: TaskRef[]         // порождённые задачи
  }
}
```

**Что это даёт со временем:**
- Система знает, что звонки Краснову обычно длятся 20 мин, а не 15
- Система знает, что подготовка презентаций занимает у вас на 30% больше оценки
- Система знает, что задачи с P3 вы переносите в 60% случаев → предлагает их реже
- Система знает, что по понедельникам у вас больше незапланированных прерываний → ставит меньше deep work

### 3.6. Reporter Agent (Отчётность)

**Роль:** Автоматическая генерация отчётов и дайджестов.

**Функции:**
- Утренний дайджест (план дня, ключевые события, дедлайны)
- Еженедельный отчёт по команде (прогресс, проблемы, метрики)
- Ежемесячный отчёт для руководства (результаты, KPI, прогнозы)
- Ad-hoc отчёты по запросу (статус проекта для заказчика)
- Подготовка данных для ежемесячных one-on-one с сотрудниками

### 3.7. Memory Agent (Управление памятью)

**Роль:** Долгосрочная память системы, обеспечивающая обучение и контекст.

**Функции:**
- Хранение и индексация истории проектов, оценок, фактических результатов
- Формирование «базы знаний» команды (решения, паттерны, антипаттерны)
- Калибровка оценок (сравнение план/факт и коррекция)
- Поиск аналогов для новых ТЗ
- Сохранение предпочтений и стиля работы руководителя

**Структура памяти:**

```
Memory Store
├── Leader Task Log                   # ВСЕ задачи руководителя из чата
│   ├── task_records[]                # полная история задач (TaskRecord)
│   ├── person_associations           # Краснов → цех 3, дефекты
│   ├── task_patterns                 # "презентация" → обычно 2ч, не 1.5ч
│   ├── day_patterns                  # понедельник = много прерываний
│   └── delegation_history            # что и кому делегировалось
│
├── Projects Archive                  # завершённые проекты с план/факт
│   ├── estimates vs actuals          # для калибровки оценок
│   ├── lessons learned               # извлечённые уроки
│   ├── decision log                  # принятые решения и их результаты
│   └── project_task_links            # какие задачи руководителя к какому проекту
│
├── Team Knowledge Base
│   ├── employee profiles             # профили, сильные стороны
│   ├── skill progression             # рост навыков во времени
│   └── collaboration patterns        # кто с кем эффективно работает
│
├── People & Contacts Graph           # карта всех упомянутых людей
│   ├── internal_contacts             # Краснов: цех 3, начальник, данные качества
│   ├── interaction_frequency         # как часто контакт с каждым человеком
│   └── context_per_person            # о чём обычно общение с этим человеком
│
├── Domain Knowledge
│   ├── metallurgy DS patterns        # типовые DS-задачи в металлургии
│   ├── data sources catalog          # доступные источники данных
│   └── stakeholder map               # карта заказчиков и их предпочтений
│
└── System Calibration
    ├── estimation accuracy           # точность оценок со временем
    │   ├── by_task_type              # quick: +5%, comm: -10%, deep: +25%
    │   └── by_project_domain         # CV-задачи: +15%, табличные: +5%
    ├── scheduling_accuracy           # как часто план дня выполняется
    │   ├── completion_rate_by_type   # quick: 90%, deep: 65%
    │   └── postpone_rate_by_priority # P3 переносятся в 60% случаев
    ├── prediction models             # модели для прогнозов
    └── feedback history              # обратная связь от руководителя
```

## 4. Взаимодействие человека и системы

### 4.1. Принципы

| Принцип | Описание |
|---------|----------|
| **Human-in-the-loop** | Система рекомендует — человек решает. Никаких автономных действий с последствиями |
| **Прозрачность** | Каждая рекомендация сопровождается обоснованием |
| **Градиент автономии** | По мере доверия руководитель может делегировать больше рутины |
| **Минимум трения** | Интерфейс через чат на естественном языке, минимум форм |

### 4.2. Типовые сценарии взаимодействия

**Утренний старт дня:**

Руководитель: "Доброе утро"

  - Встреча с заказчиком "Оптимизация шихты" в 14:00

  ВАШИ ЗАДАЧИ НА СЕГОДНЯ (13 задач → сгруппированы):

  ┌─ DEEP WORK (2ч 30мин) ──────────────────────────────────────┐

  Буфер: 3ч 45мин свободно для незапланированного

**Анализ нового ТЗ:**
```
Руководитель: "Оцени ТЗ из файла tz_predicting_defects.pdf"
Система:
  Анализ ТЗ: Предсказание дефектов литья

  Суть: Классификация дефектов по данным датчиков + история качества
  Сложность: L (сбор данных + feature engineering + модель + интеграция)

  Декомпозиция:
  1. Сбор и анализ данных         — 24-40ч (риск: качество данных)
  2. Feature engineering           — 16-24ч
  3. Обучение и валидация модели  — 20-32ч
  4. Интеграция в pipeline         — 16-24ч
  5. Документация и передача       — 8-12ч

  Итого: 84ч (оптим.) → 112ч (ожид.) → 148ч (пессим.)
  Рекомендуемый срок: 4-6 недель при 1 выделенном специалисте

  Риски:
  ⚠ ВЫСОКИЙ: Качество исторических данных — нет гарантии полноты
  ⚠ СРЕДНИЙ: Зависимость от IT-отдела для доступа к данным датчиков
  ⚡ НИЗКИЙ: Модель может не дать нужную точность с первой итерации

  Аналогичный проект: "Предсказание качества проката" (Q2 2025)
    → оценка была 96ч, факт 124ч (+29%), основная причина — задержки данных

```

## 5. Самообучение и улучшение

### 5.1. Цикл обратной связи

```
Оценка ТЗ → Выполнение проекта → Сравнение план/факт → Калибровка модели
     ↑                                                          │
     └──────────────────────────────────────────────────────────┘
```

### 5.2. Механизмы обучения

| Механизм | Что улучшает | Как работает |
|----------|-------------|-------------|
| **Калибровка оценок** | Точность прогнозов сроков | Сравнение план/факт по каждому проекту, расчёт коэффициента коррекции по типам задач |
| **Профилирование команды** | Рекомендации по назначению | Накопление данных о скорости и качестве работы каждого сотрудника по типам задач |
| **Обучение на решениях** | Приоритизация и рекомендации | Фиксация решений руководителя, когда они отклоняются от рекомендаций — и анализ почему |
| **Рефлексия по рискам** | Оценка рисков | Какие риски сработали, какие нет — обновление вероятностей |
| **Feedback loop** | Общее качество | Руководитель оценивает полезность рекомендаций (👍/👎) — система корректируется |

### 5.3. Пример калибровки

```
Проект "Предсказание качества проката" (завершён):
  Оценка системы:  96 часов
  Факт:            124 часа (+29%)
  Причина:         Задержки с данными (+20ч), доработка модели (+8ч)

  → Система обновляет:
    - Коэффициент для задач с внешними зависимостями по данным: 1.0 → 1.2
    - Буфер на итерации модели для задач CV: +10%
    - Рекомендация: закладывать 2 итерации по умолчанию для новых предметных областей
```

## 8. Ключевые принципы системы

1. **Человек решает, система помогает** — Никаких автономных действий. Система даёт рекомендации с обоснованием.

2. **Данные побеждают интуицию** — Каждая рекомендация подкреплена фактами из истории проектов и текущих метрик.

3. **Прозрачность > Магия** — Руководитель всегда понимает, почему система рекомендует то или иное действие.

4. **Инкрементальное доверие** — Система начинает с минимальной автономии и наращивает её по мере доказанной полезности.

5. **Контекст металлургии** — Система понимает специфику DS-задач в металлургии (данные с датчиков, предиктивное качество, оптимизация процессов, предсказание поломок).
